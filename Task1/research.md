# Задание 1. Исследование моделей и инфраструктуры

Все цифры в документе воспроизводимые:
скрипты замеров — в `Task1/benchmarks/`, сырые результаты — в
`Task1/benchmarks/results/`.

## Кто задаёт задачу и что на неё влияет

Задачу ставит руководство QuantumForge (C-level, Хельсинки): им нужны не
«красивый бот», а снижение FTE-затрат на поиск информации, ускоренный
онбординг и подготовка к SOC 2. Пользователей четыре группы: разработчики
ищут ADR и API-доки, саппорт — решения типовых проблем, менеджеры и аналитики
— регламенты, новые сотрудники — onboarding. Отдельные стейкхолдеры — GRC
(140 часов ручной сверки политик в год) и HR (опрос: новые инженеры тратят
до 4 часов в неделю на «раскопки»). Интерфейс — Telegram, это условие проекта.

### Масштаб данных

База — около 21K документов: 18K Markdown/MDX в монорепозитории, 3K страниц
Confluence, 250 PDF-спецификаций. При чанковании 200–300 слов это примерно
70–100K чанков; в расчётах дальше используем верхнюю границу — 100K.

### Что нельзя уносить в облако

В базе лежат материалы под NDA с ABB и Wärtsilä (PDF-спецификации заказных
проектов), ADR и архитектурные решения, интеграции с SCADA клиентов и
внутренние политики (GDPR, SOC 2). Поэтому главный принцип всех решений
ниже: **по умолчанию весь pipeline живёт в периметре компании** (AWS-аккаунт
QuantumForge, EU-регион), а в облачные API уходит только то, что явно
помечено как открытое. Это ограничение, а не оптимизация — именно оно
определяет большую часть выбора.

## 1. LLM: локальные или облачные

### Качество

| Модель | Класс качества | Комментарий |
| --- | --- | --- |
| GPT-6 Astra / GPT-5.6 Sol | frontier | лучший класс для сложного multi-hop рассуждения; для «вопрос-ответ по БЗ» избыточны |
| GPT-5.6 Terra | верхний средний | закрывает ~90% корпоративного QA; хорошо следует инструкциям — важно для CoT и few-shot из Задания 4 |
| GPT-5.6 Luna | средний, самый дешёвый | простые извлекательные ответы; на многоступенчатых связках слабее |
| YandexGPT Pro 5.1 | верхний средний | сильная русская генерация; английский ниже класса GPT-5.6 |
| YandexGPT Lite | средний | быстрый и дешёвый, простые вопросы |
| Qwen3 8B / Llama 3.1 8B | ниже среднего | отстают от frontier на 15–20 п.п. по MMLU/IFEval; простые RAG-ответы с хорошим промптом — ок, сложные связки и RU — заметные галлюцинации |
| Qwen3 14B | средний | ближе к Terra в EN; RU всё равно слабее YandexGPT Pro |
| Qwen3.8 27B | выше среднего, близко к frontier для своего класса | GPQA Diamond 89.2, SWE-bench Pro 61.7, Terminal-Bench 2.1 — 73.0; независимые оценки: «приближается к SOTA начала 2026»; самая сильная локальная опция в EN, RU — многоязычная, но слабее YandexGPT Pro |

Два наблюдения. Первое: в нашем сценарии качество определяет в первую
очередь retrieval-слой, а не LLM — даже средняя модель даст хороший ответ,
если в промпт подставлены правильные 4–6 чанков, и плохой, если чанки
нерелевантны. Разрыв между 8B и frontier чувствуется на мультидокументных
вопросах (сопоставить ADR + API-доки + регламент). Второе: 27B заметно
сужает этот разрыв — по бенчмаркам она конкурентна Terra и Sonnet-классу на
рассуждениях, оставаясь self-hosted. Документация QuantumForge ведётся
преимущественно на английском, поэтому локальная 27B — разумный основной
движок; 8B оставляем как fallback на случай строгого SLO по латентности.

### Скорость

| Сценарий | 8B на GPU 24 GB | 27B на GPU 24 GB (Q4) | 8B на CPU | GPT-5.6 (API) | YandexGPT (API) |
| --- | --- | --- | --- | --- | --- |
| Time-to-first-token | 0.3–1 с | 0.5–2 с | 3–10 с | 0.5–2 с | 1–3 с |
| Скорость генерации | 30–60 ток/с | 15–30 ток/с (MTP) | 5–15 ток/с | 40–100 ток/с | 20–50 ток/с |
| Ответ ~150 токенов | 2–5 с | 5–10 с (reasoning_effort medium/low) | 10–30 с | 2–6 с | 4–8 с |

По 27B: Q4-квант занимает 16–18 GB VRAM, на 24 GB GPU остаётся запас под
KV-cache — хватает на контекст 8–16K токенов. Для RAG-пайплайна этого
много: system prompt + 5–6 чанков + ответ — это 4–8K. Полный 262K контекст
уже требует 32–48 GB (вариант C в разделе 4). И главное: GPU обязателен.
На CPU 8B отвечает за 10–30 секунд, 27B — за минуты, для чат-бота это
неприемлемо.

### Стоимость

Допущения: 100 активных пользователей × 10 запросов в неделю, итого ~40K
запросов в месяц; в запросе ~2K input-токенов (system prompt + 5 чанков)
и ~300 output-токенов.

| Вариант | Тариф | 40K запросов/мес |
| --- | --- | --- |
| GPT-5.6 Luna | $0.20 / $1.20 за M токенов | ~$30 |
| GPT-5.6 Terra | $2.00 / $12.00 за M токенов | ~$310 |
| GPT-5.6 Sol | $5.00 / $30.00 за M токенов | ~$780 |
| YandexGPT Lite | 0.20 ₽/1K токенов (≈ $2.35/M)¹ | ~$220 |
| YandexGPT Pro 5.1 | 0.80 ₽/1K токенов (≈ $9.42/M)¹ | ~$880 |
| Локальная 8B или 27B Q4 (on-demand) | g6.2xlarge ≈ $0.98/ч, 27B Q4 (~16–18 GB) влезает в те же 24 GB | ~$715 фиксированно, 0 за запросы |
| Локальная (Savings Plan) | −30…−60% | ~$400–550 фиксированно |

¹ Курс ЦБ РФ на 2026-10-06 — 84.93 ₽/USD; цены YandexGPT — по странице
тарификации AI Studio, сверка от 2026-07-18, конвертация ориентировочная.

Облачный LLM — переменная стоимость, растущая с трафиком; локальный —
фиксированная аренда. Точка безубыточности локальной модели (~$715/мес)
против Terra — примерно 90K запросов в месяц; при нашем 40K Terra дешевле
по деньгам. Но решение принимает не цена, а конфиденциальность: документы
должны оставаться в периметре, так что облако по умолчанию отпадает.

### Развёртывание

| Критерий | Локальная (HF) | OpenAI | YandexGPT (AI Studio) |
| --- | --- | --- | --- |
| До первого ответа | 1–2 дня: вес 4–18 GB, настройка vLLM/SGLang, Docker | минуты: API key | часы: сервисный аккаунт, роль, folder_id, ключ |
| Операционная нагрузка | выше: GPU-мониторинг, OOM, обновление весов | нулевая, managed | низкая, но есть квоты (10 параллельных sync, 10 rps async) |
| Данные покидают периметр | нет | да; EU-обработка — +10% к цене для моделей с марта 2026, Azure OpenAI даёт data residency, но дороже | да, и это Yandex Cloud в РФ |

Последняя строка про YandexGPT — отдельная боль. QuantumForge — финско-
эстонская компания, и передача данных в РФ — трансферт вне EEA. YandexGPT
остаётся в картине только как вариант для RU-документов при согласованном
DPA; по умолчанию из конфигурации исключаем.

### Что берём

Основной движок — **локальная Qwen3.8 27B (Q4) через vLLM/SGLang на 24 GB
GPU**: качество mid-tier закрытых моделей, данные не покидают периметр,
токены бесплатны. 5–10 секунд на ответ для корпоративного чата — нормально.
Для открытых корпоративных документов оставляем опциональный маршрут на
**GPT-5.6 Terra**, а **8B** — fallback, если когда-нибудь потребуется SLO
ниже 5 секунд (помещается на ту же ноду).

## 3. Векторные базы: FAISS, ChromaDB, Qdrant

### Замеры

`Task1/benchmarks/bench_vecdb.py`: 10K векторов × 384 dim (normalized,
cosine), 200 запросов, k=5, 32 CPU / 62 GB RAM, без GPU.

| Метрика | FAISS (IndexFlatIP) | ChromaDB (HNSW, SQLite) | Qdrant (local mode, HNSW) |
| --- | --- | --- | --- |
| Индексация 10K векторов | 2 мс | 0.9 с | 17.7 с |
| Сохранение | 13 мс, один файл 15.4 MB | write-through | write-through |
| Загрузка | 5 мс | 2 мс | 0.2 с |
| Поиск p50 | 0.17 мс | 0.51 мс | 6.3 мс |
| Поиск p95 | 0.26 мс | 0.59 мс | 7.6 мс |
| Прирост RAM | +18 MB (сам индекс: 10K×384×4B) | +104 MB | +256 MB |


Все три варианта с огромным запасом укладываются в 50-миллисекундный
бюджет retrieval-слоя: на 100K чанков flat-поиск FAISS займёт ~2–3 мс,
HNSW у Chroma и Qdrant — ~10–20 мс. То есть скорость не является аргументом
«за» или «против» ни одного из трёх — различия проявляются в операционке.

### Как каждый ведёт себя в работе

**FAISS** — это библиотека, а не сервис. Встроенных метаданных, фильтров
и удаления нет: метаданные храним рядом (JSONL по chunk_id), обновление
индекса — пересборкой (у нас это миллисекунды на 10K и пара секунд на 100K).
Взамен — минимум того, что может сломаться: один файл, атомарная замена,
никаких демонов, версионирования хранилища и lock-файлов.

**ChromaDB** — дружелюбная база данных: add/query/delete/get, метаданные
и фильтрации из коробки, удобно в разработке. Но под капотом SQLite +
HNSW + Python-обёртка — больше движущихся частей; server-mode это уже
отдельный контейнер со своим SLO.

**Qdrant** — полноценная Rust-база: самая развитая фильтрация по
метаданным, distributed-режим, production-grade API. В нашем замере — самый
тяжёлый по RAM (+256 MB, это встроенный сервер) и самый медленный на
индексации с дефолтами. Это плата за то, что мы получаем настоящую БД
вместо массива в памяти.

### Почему FAISS

1. 100K чанков — это 154 MB в RAM и поиск за 2–3 мс. Это «массив в памяти»,
   а не база данных: отдельный сервис здесь не нужен, функции персистентности
   и обновления закрываются одним файлом и атомарной заменой.
2. Ежедневное обновление (Задание 6) тривиальное: собираем новый индекс во
   временной папке, `os.replace()`, бот подхватывает. Ни одного
   delete/insert в «живой» БД и ни одного окна неактуальности.
3. Один контейнер, один volume, нет лишних портов и сервисов.
4. Ноль лицензионных затрат, минимальный footprint (<200 MB RAM).

минусы: нет встроенной metadata-фильтрации — если понадобится
«показывать только документы раздела X» или per-contractor ACL, придётся
фильтровать после поиска (oversampling k×3) либо переходить на Qdrant;
и нет встроенного аудита индекса — ведём его в логах обновления (Задание 6).

### Когда Qdrant станет правильным выбором

Когда появятся хотя бы два из: сложные фильтры по метаданным прямо в поиске
(раздел, роль, клиент); удаление и обновление без полного пересборки;
несколько реплик и распределённый доступ; миллион+ чанков; внешний API к
индексу для других сервисов. На этом этапе меняем только адаптер
хранилища — пайплайн «чанки → эмбеддинги → индекс» остаётся тем же.
Сейчас Qdrant избыточен: мы платили бы RAM и сложностью за то, чем не пользуемся.

## 4. Конфигурация сервера

Общее: бот живёт в AWS компании (EU-регион), Docker Compose (`bot` +
`vllm` + volume с индексом), эмбеддинги локальные, FAISS. Цены on-demand
(us-east-1), Savings Plans дают ещё −30–40%.

| Вариант | Конфигурация | LLM | ~Стоимость/мес |
| --- | --- | --- | --- |
| A. Пилот (без GPU) | 4 vCPU / 16 GB (m6i.xlarge, ~$0.19/ч) | облачная Terra по API | ~$140 + ~$310 API |
| B. Базовый локальный (рекомендуем) | 8 vCPU / 32 GB + 1× L4 24 GB (g6.2xlarge, ~$0.98/ч) | локальная 27B Q4 (16–18 GB VRAM, контекст 8–16K) | ~$715–890 (SP ~$500–600) |
| C. Продакшн | 8 vCPU / 64 GB + 1× L40S 48 GB (g6e.2xlarge, ~$2.24/ч) | 27B с контекстом 64K+ и высокой конкурентностью | ~$1640 (SP ~$1100) |
| D. Гибридный | как B + роутер по метке документа | 27B (конфиденциальные) + Terra (открытые) | ~$715 + ~$310 API |

Несколько слов про варианты. A — самый дешёвый и простой, но он отправляет
документы в OpenAI; допустим только если юридический отдел подтвердит, что
пилотная БЗ не содержит ничего конфиденциального. B — покрывает
конфиденциальность и даёт интерактивные 5–10 секунд; GPU здесь не роскошь,
а обязательство (без него 27B отвечает за минуты). Апгрейд 8B → 27B на этой
ноде «бесплатный»: Q4-веса 27B влезает в те же 24 GB. C — когда понадобятся
длинный контекст (64K+), высокий RPS или Q8-качество. D — «лучшее из двух
миров» с роутингом, но это лишний компонент, который нужно эксплуатировать.

**Выбираем B.** Если пилот стартует только с открытыми документами —
начинаем с A и переходим на B заменой одной строки в compose.

## 5. Итоговый стек

| Слой | Выбор | Альтернатива / путь роста |
| --- | --- | --- |
| LLM (основная) | Qwen3.8 27B (Q4), vLLM/SGLang, GPU 24 GB, контекст 8–16K, reasoning_effort medium/low, в периметре | 8B — если нужен SLO <5 с; Terra — для открытых доков; YandexGPT Pro 5.1 — только с DPA, для RU |
| LLM (fallback) | GPT-5.6 Terra API | Luna — дешёвые high-volume задачи |
| Эмбеддинги | all-MiniLM-L6-v2, CPU, 384 dim | bge-base-en-v1.5; 3-small — если доки открыты |
| Чанкирование | RecursiveCharacterTextSplitter, 200–300 слов, overlap 15–20% (детали — Задание 3) | — |
| Векторная БД | FAISS IndexFlatIP, файл `.index` + JSONL-метаданные | Qdrant — при фильтрации в поиске, >1M чанков, ACL |
| Инфраструктура | 8 vCPU / 32 GB / 1× L4 24 GB, AWS EU, compose: `bot` + `vllm` + volume | пилот: 4 vCPU / 16 GB без GPU |
| Обновление индекса | полный реиндекс + атомарная замена файла (Задание 6) | — |
| Конфиденциальность | `confidential=true` → только локальная LLM; API — только открытые | роутер по меткам (вариант D) |

Пара абзацев о том, почему связка именно такая. FAISS + локальные
эмбеддинги: весь pipeline (индекс, эмбеддинги, LLM) остаётся в периметре
QuantumForge, и ни один байт клиентских спецификаций, ADR или SCADA-доков не
покидает AWS-аккаунт в EU. На масштабе 100K чанков FAISS — это 154 MB в RAM
и 2–3 мс на поиск, и «база данных» как отдельный компонент здесь просто не
нужна: один файл, один volume, один контейнер. Это минимум операционной
поверхности для пилота, который должен жить без постоянного DevOps-присмотра.

Qwen3.8 27B + опционально Terra: конфиденциальность исключает облако как
default, а 27B в Q4 даёт качество mid-tier закрытых моделей (GPQA 89.2,
SWE-bench Pro 61.7) на том же GPU 24 GB, что и 8B, — инфраструктурная
стоимость не растёт, растёт качество. Ответ за 5–10 секунд интерактивен для
корпоративного чата, а стоимость фиксированная и не зависит от трафика.
Последующие переходы — облачные эмбеддинги для открытых доков, Qdrant при
росте, нода 48 GB для длинного контекста — проектируются как замена
адаптеров, а не пересборка.
